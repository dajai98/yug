# Phase 3 source candidate intake v1

The sealed [review catalog](../../training/specifications/phase3_source_candidate_registry_v1.json) records the 47 rows supplied in `yug_phase3_source_candidates_v1.json` (input SHA256 `15f74a8b4c3c3efdf91976c57351cb755f409f70ffa0255defb7220718854966`). It uses the existing source-registry schema so the offline `source_expansion` screen can read it. It is **not** the active production registry: the active `source_registry_v1.json`, its production-spec identity, category allocations, and approval rules are unchanged.

Forty-one new source IDs are retained as `REVIEW` only. Six supplied rows match existing registry sources by ID or locator and are recorded in `existing_registry_matches` without changing those sources. One of these is a second category proposal for the already registered ripgrep repository. Shared upstream locators among review rows receive the same conservative source/split group, but no split or production token cap is assigned.

The original 47 candidate rows are retained as `submitted_candidate` review metadata. Their statuses, license labels, URLs, notes, and scope descriptions are **candidate claims**, not verified license or provenance evidence. No row supplies an immutable revision or per-file/document clearance. Each new row has no verified license, revision, allowed path, clearance record, or production capacity, and cannot be prepared, approved, downloaded, or accounted from this catalog. In particular, `ACCEPT_CANDIDATE` is not YUG `ACCEPT`, and a source that was already accepted in the active registry acquires no new approval or category route from this intake.

Any later use must independently establish exact identity, licensing and rights scope, file/document evidence, category ownership, protected-reference exclusions, split and approval through the existing gates. Conditional, benchmark-sensitive, and synthetic/derivative proposals retain their existing policy requirements. This intake neither fetches metadata nor dataset payloads.
