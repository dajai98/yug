# YUG corpus operator commands v1

Phase 3 review-only command addendum checked against live modules on 2026-10-29.

This inventory was checked against the live `training/` modules and `pyproject.toml` on 2026-10-28. It documents commands; it does **not** authorize acquisition, admission, commercial training, or a policy change. Run from the repository root with the environment's `python` (and the `dataset` optional dependency for Parquet transport). Replace every `<...>` placeholder with a separately reviewed path or externally approved digest. All output paths shown under `artifacts/` are local, ignored operational state; use **new** output directories for new requests. A clean Git checkout does not contain the historical production caches, held-out inventory, approved grants, governance log, or ledger. Supply those external inputs explicitly, rather than treating a path printed in an old report as available or authoritative.

**Working-tree qualification (2026-11-04):** the named Phase 2 modules, including `training/cumulative_accounting.py`, `training/historical_corpus_import.py`, `training/approval_governance.py`, and `training/category_ownership.py`, are tracked at current HEAD. Several live Phase 3 clearance/evidence modules, tests, schemas, and this guide's changes remain outside that checkpoint. A clean checkout needs a reviewed Phase 3 software checkpoint and separately preserved ignored evidence inputs before reproducing the live command/gate surface; this guide does not stage or commit them.

**Classes:** `RO` = read-only/introspection; `DRY` = no payload acquisition but may write local diagnostic state; `W` = writes local state; `NET` = network access when the stated opt-in flag is used; `TA` = can produce token/shard artifacts. `Ledger` says whether the command can change the cumulative production ledger; it does not mean the command approves a source. `--resume` always means repeat the *same pinned inputs* in the same output directory, never overwrite an earlier completed scope.

## Discovery and review-cache commands

### 1. GitHub source discovery — `training/source_discovery.py`

- Purpose/class: bounded, revision-resolving GitHub metadata and root-license discovery; `W`, `NET` **only** with `--fetch`. No source payloads, training artifacts, or ledger mutation. No prior source approval required.
- Required: `--output`; give `--seeds` explicitly (JSON array, 1–10 entries containing `locator`, simple `branch`, valid `category` and `subcategory`). Optional: `--registry`, `--spec`, `--fetch`, `--resume`.
- Inputs/outputs: sealed active or review registry and spec, seed JSON; writes `request.json`, retained per-source metadata/license responses, `decisions.json`, `catalog.json`, `complete.json` under `--output` in `artifacts/`. `--resume` verifies retained metadata and request identity. Without `--fetch`, missing metadata fails closed. An accepted metadata row is **not** per-file clearance.
- Safe check: `python -B -m training.source_discovery --help`.
- Later metadata-only template: `python -B -m training.source_discovery --registry <REGISTRY> --spec <SPEC> --seeds <GITHUB_SEEDS_JSON> --output artifacts/<NEW_DISCOVERY> --fetch`.

### 2. Hugging Face dataset discovery — `training/dataset_discovery.py`

- Purpose/class: bounded dataset metadata/license discovery and immutable revision lookup; `W`, `NET` only with `--fetch`; zero payload bytes, no ledger mutation or prior approval.
- Required: `--seeds` (1–10 `dataset_id`/`category`/`subcategory` records), `--output`. Optional: `--registry`, `--spec`, `--fetch`, `--resume`.
- Inputs/outputs: registry/spec and seed JSON; retained metadata, `catalog.json`, `decisions.json`, request and completion receipts under `artifacts/<OUTPUT>`. `--resume` checks pins/hashes. Ambiguous, conditional or incompatible license metadata does not clear records; non-benchmark status is not established by this command.
- Safe check: `python -B -m training.dataset_discovery --help`.
- Later metadata-only template: `python -B -m training.dataset_discovery --registry <REGISTRY> --spec <SPEC> --seeds <HF_SEEDS_JSON> --output artifacts/<NEW_DATASET_DISCOVERY> --fetch`.

### 3. Source-candidate intake/screen — `training/source_expansion.py`

- Purpose/class: offline screen of a **sealed registry-format catalog** against existing preparation rules; `W` for local decisions, no network, payloads, shards or ledger mutation. No approved source required. A `CANDIDATE` means review-cache eligibility only.
- Required: `--output`; optional `--registry`, `--spec`, `--resume`. Inputs are the sealed catalog and frozen spec. Outputs: `request.json`, `candidates.json`, `decisions.json`, `complete.json` under `artifacts/`. Replay rehashes inputs and outputs.
- Safe diagnostic using the current review intake: `python -B -m training.source_expansion --registry training/specifications/phase3_source_candidate_registry_v1.json --spec training/specifications/production_corpus_v1.json --output artifacts/<NEW_SCREEN_DIR>`; it presently rejects all 41 new unpinned/unlicensed rows, by design.
- Later review-cache template: `python -B -m training.source_expansion --registry <SEALED_PINNED_CATALOG> --spec <SPEC> --output artifacts/<NEW_EXPANSION>`.
- **No generic candidate-import CLI exists.** The 47-row Phase 3 intake was recorded as a sealed review catalog, not added to the active registry. This command does not pin, fetch metadata for, approve, or allocate those rows.

### 4. Git repository cache preparation — `training/source_prepare.py`

- Purpose/class: classify or fetch exact pinned GitHub commits into a bounded review cache; `DRY` with `--dry-run` (creates output directory but downloads nothing), otherwise `W+NET`; no production tokens or ledger mutation. Cache eligibility needs a GitHub locator, 40-hex commit, supported license evidence and accepted/conditional review status; it is **not** production approval.
- Optional flags: `--registry`, `--spec`, `--output`, `--dry-run`, `--resume`, `--limit` (source count), `--retries`. Inputs: sealed catalog/spec. Outputs: per-source bare Git cache, content-addressed files, `inventory.jsonl`, request/config/completion receipts under `artifacts/`. Resume verifies Git objects, inventory and cached file hashes; vendor/generated/binary/path exclusions stay unresolved or excluded.
- Safe classification: `python -B -m training.source_prepare --registry training/specifications/phase3_source_candidate_registry_v1.json --spec training/specifications/production_corpus_v1.json --output artifacts/<NEW_PREP_CHECK> --dry-run`.
- Later cache template: `python -B -m training.source_prepare --registry <PINNED_DISCOVERY_CATALOG> --spec <SPEC> --output artifacts/<NEW_REVIEW_CACHE> --limit <N>`; add `--resume` only for the same cache request. This downloads repository objects, not approved corpus data.

### 5. Immutable file clearance evidence — `training/clearance_evidence.py`

- Purpose/class: deterministic offline `EVIDENCED`/`EXCLUDED`/`REVIEW` decisions for verified cached files; `DRY` with `--dry-run` (no evidence publication), otherwise `W`; no network, shards or ledger mutation. `EVIDENCED` requires an **existing exact per-file grant**; root license alone is insufficient.
- Required: `--cache`, `--output`; optional `--dry-run`, `--resume`, `--limit` (total decisions). The grant-backed path uses the active registry/spec plus retained approved registry/spec/plan and references under `artifacts/`. For newly discovered review caches, use explicit `--review-only --cache-registry <SEALED_PREPARATION_CATALOG> --references <CURRENT_PROTECTED_REFERENCE_INVENTORY>`; this validates the current spec and cache status, imports no historical grants, and cannot emit `EVIDENCED`. The protected-reference input must use the current supported schema; the historical Phase 1 JSONL is not a substitute. Outputs: request, SQLite checkpoint, `evidence.jsonl`, `complete.json`. Resume revalidates pinned inputs and committed decisions.
- Safe syntax check: `python -B -m training.clearance_evidence --help`.
- Current review-only form: `python -B -m training.clearance_evidence --cache <VERIFIED_CACHE> --cache-registry <SEALED_DISCOVERY_CATALOG> --references <CURRENT_PROTECTED_REFERENCES> --review-only --output artifacts/<NEW_REVIEW_EVIDENCE> --dry-run`. Omit `--dry-run` only to publish review evidence; this route imports no historical grant and cannot emit `EVIDENCED`.
- Later offline template: `python -B -m training.clearance_evidence --cache artifacts/<VERIFIED_CACHE> --output artifacts/<NEW_FILE_EVIDENCE> --dry-run` (requires the separately supplied approved inputs even in dry-run).

### 5a. Retained protected-reference migration — `training/protected_reference_migration.py`

- Purpose/class: offline one-to-one compiler for the retained 59 Phase 1 and 32 GSM8K holdout items; `W`, no network, production grant, token/shard output, or ledger mutation. It emits 155 linked current-schema records and a sealed manifest. It is not a general inventory builder.
- Required: `--output` (new directory). Its historical inputs are fixed under `artifacts/acquisition_readiness_gate_v1/`, `artifacts/gsm8k_admission_v1/`, `artifacts/tokenizer_fit_sample_gate_v1/`, and `artifacts/tokenizer_transfer_gate_v1/`. A clean checkout must restore verified external copies at those paths. There is no `--resume` flag; rerunning an identical completed output verifies and reuses it.
- Safe syntax check: `python -B -m training.protected_reference_migration --help`.
- Later offline template: `python -B -m training.protected_reference_migration --output artifacts/<NEW_PROTECTED_INVENTORY>`.

### 6. Existing-grant source admission — `training/source_admission.py`

- Purpose/class: match a verified cache to immutable grants and held-out groups; `W+DRY` (writes decisions, approved-scope plan and production preflight), no network, tokens or ledger mutation. It does **not** create new grants.
- Required: `--cache`; optional: `--output`, `--evidence`, `--registry`, `--spec`, `--approved-registry`, `--approved-spec`, `--approved-plan`, `--references`. Supply every approved/reference path explicitly on a clean checkout. Inputs are sealed caches, approved grant universe and references. Outputs: `decisions.jsonl`, `registry.json`, `spec.json`, `plan.jsonl`, `dry_run.json`, `complete.json` in `artifacts/`. No `--resume` flag; completed output is checked on rerun rather than silently replaced. Missing/changed grant, evidence or holdout state fails closed.
- Safe syntax check: `python -B -m training.source_admission --help`.
- Later preflight template: `python -B -m training.source_admission --cache artifacts/<CACHE> --evidence artifacts/<EVIDENCE> --approved-registry <APPROVED_REGISTRY> --approved-spec <APPROVED_SPEC> --approved-plan <APPROVED_PLAN> --references <PROTECTED_REFERENCES> --output artifacts/<NEW_ADMISSION_PREFLIGHT>`.

### 7. New narrow Python-file grant materialization — `training/source_approval.py`

- Purpose/class: offline evidence-based approval of selected Python `src/` package files under its supported package-declaration or narrow MIT file-attribution profile; `W+DRY`, no network, corpus tokens, or ledger mutation. This is **not** a general repository/dataset approval command.
- Required: `--output`; supply `--cache`, `--catalog`, `--evidence`, `--registry`, `--spec`, `--plan`, `--references` explicitly. Optional: `--cap`, `--validation-groups`, `--resume`. Inputs: verified Git cache and evidence, existing approved universe, holdouts. Outputs: sealed new `registry.json`, `spec.json`, file manifests, source-clearance records, `decisions.json`, `plan.jsonl`, `dry_run.json`, `complete.json` under `artifacts/`. It assigns bounded caps/splits; ambiguous paths remain REVIEW/EXCLUDED. `--resume` compares retained input/output identities. Production still needs independent plan and ownership approval pins.
- Safe syntax check: `python -B -m training.source_approval --help`.
- Later approval-preflight template: `python -B -m training.source_approval --cache artifacts/<VERIFIED_CACHE> --catalog <PINNED_CATALOG> --evidence artifacts/<EVIDENCE> --registry <EXISTING_APPROVED_REGISTRY> --spec <EXISTING_APPROVED_SPEC> --plan <EXISTING_APPROVED_PLAN> --references <PROTECTED_REFERENCES> --output artifacts/<NEW_APPROVAL_PROPOSAL> --cap <REVIEWED_CAP>`.

### 7a. Review-only file-grant dossiers — `training/source_grant_proposals.py`

- Purpose/class: offline `W` compiler of sealed per-file review dossiers from complete review-only clearance; no network, approval, production grant, tokens, shards, or ledger mutation. Existing Python package and narrow MIT file-attribution checks can flag evidence candidates, but every output remains ungranted. It does not make non-Python or conditional sources production-eligible.
- Required: `--cache`, `--catalog`, `--evidence`, `--references`, `--output` (new directory under `artifacts/`). The inputs must bind the current active spec/registry, sealed cached catalog, complete review-only evidence, and current protected references exactly. Outputs: `request.json`, `proposals.jsonl`, `complete.json`. There is no `--dry-run` or `--resume` flag; an identical completed output is checked on rerun.
- Safe syntax check: `python -B -m training.source_grant_proposals --help`.
- Later offline template: `python -B -m training.source_grant_proposals --cache <VERIFIED_CACHE> --catalog <SEALED_DISCOVERY_CATALOG> --evidence <COMPLETE_REVIEW_ONLY_EVIDENCE> --references <CURRENT_PROTECTED_REFERENCES> --output artifacts/<NEW_GRANT_DOSSIER>`.
- A dossier is not an approved per-file grant. Do not pass it to `source_admission` as an approved registry/spec/plan or count its candidate files as `EVIDENCED`.

### 7b. Externally reviewed first-time source clearance — `training/source_first_clearance.py`

- Purpose/class: offline `W` materialization of an **exact-file** first-time repository decision; no network, corpus tokens, shards, ledger mutation or training authorization. This route is separate from revision supersession and never selects candidates or approves a root license by itself.
- Required: `--decision`, `--approved-decision-sha256`, `--cache`, `--catalog`, `--review`, `--references`, `--output` (new directory under `artifacts/`). The SHA256 must be supplied as an external governance pin. Each selected file must have a separately hash-pinned first-party rights review; the decision must bind exact source, revision, path, content hash, owner, license, source-scope evidence and attribution obligations. Missing or conflicting evidence fails closed.
- Output: exact-file manifest, source clearance, ownership records, registry/spec overlay, plan and `complete.json`. Repeating the same decision verifies byte-identical output; a changed decision needs a new output and external approval. Downstream production approval, screening and authorization gates remain separate.
- Safe syntax check: `python -B -m training.source_first_clearance --help`.
- Later offline template: `python -B -m training.source_first_clearance --decision <REVIEWED_DECISION> --approved-decision-sha256 sha256:<EXTERNAL_PIN> --cache <VERIFIED_CACHE> --catalog <SEALED_DISCOVERY_CATALOG> --review <COMPLETE_REVIEW_ONLY_EVIDENCE> --references <CURRENT_PROTECTED_REFERENCES> --output artifacts/<NEW_FIRST_CLEARANCE>`.

## Dataset evidence commands

### 8. Pinned dataset transport — `training/dataset_transport.py`

- Purpose/class: bounded Hugging Face Parquet/JSONL review transport and document extraction; `W+NET` with `--fetch` (without it, only a complete local cache can replay). It does not admit data or mutate the ledger. Requires accepted **metadata** with exact revision/license evidence, but **not** production-cleared documents.
- Required: `--catalog`, `--output`; optional `--spec`, `--limit` (1–1000 documents/source, default 32), `--budget-mib` (1–1024, default 384), `--selection` (exact dataset revision/path map), `--fetch`, `--resume`. Supports at most two sources/request and pinned LFS hashes; oversized local payloads are not materialized beyond the file limit—supported large JSONL uses verified chunks. Parquet decoding needs `pyarrow`.
- Inputs/outputs: sealed discovered catalog, spec and retained dataset metadata; under `artifacts/`, writes payload/cache chunks, per-row canonical JSON files and `inventory.jsonl`, request/metadata/completion receipts. Resume validates payload and row hashes; `--fetch` may download dataset payloads and bounded metadata.
- Safe syntax check: `python -B -m training.dataset_transport --help`.
- Later review-transport template: `python -B -m training.dataset_transport --catalog <PINNED_HF_CATALOG> --spec <SPEC> --selection <PINNED_PAYLOAD_SELECTION> --output artifacts/<NEW_DATASET_CACHE> --limit <N> --budget-mib <MIB> --fetch`.

### 9. Per-document dataset proof — `training/dataset_clearance.py`

- Purpose/class: verify exact transported rows against pinned payload/cache and existing clearance evidence, classifying `CLEAR`/`EXCLUDE`/`REVIEW`; `W`, no network, shards or ledger mutation. A dataset-level metadata license never auto-clears a row.
- Required: `--cache`, `--catalog`, `--spec`, `--evidence`, `--output`; optional `--resume`. Inputs: complete transport cache and complete `clearance_evidence` bundle. Outputs: `request.json`, `decisions.jsonl`, `complete.json` under `artifacts/`. Resume re-verifies source payload, row order, hashes and evidence binding. `CLEAR` is still **not** production admission.
- Safe syntax check: `python -B -m training.dataset_clearance --help`.
- Later offline template: `python -B -m training.dataset_clearance --cache artifacts/<VERIFIED_DATASET_CACHE> --catalog <PINNED_HF_CATALOG> --spec <SPEC> --evidence artifacts/<DOCUMENT_EVIDENCE> --output artifacts/<NEW_DOCUMENT_PROOF>`.

### 10. Dataset rights-scope resolution — `training/dataset_rights_scope.py`

- Purpose/class: bind an exact document proof to exact-revision dataset-card/license scope; `W`, no network, training artifacts or ledger mutation. Only a narrow original-dataset MIT card profile can produce `CLEAR`; synthetic/derivative or conditional rights stay REVIEW unless independently proved. `--provenance-assessment` records claims, not a new grant.
- Required: `--documents`, `--catalog`, `--cards`, `--cache`, `--output`; optional `--resume`, `--provenance-assessment`. Inputs: verified document proofs, dataset catalog/cache, **externally retained exact-revision README/card receipts**. Outputs: per-source scope JSON, `decisions.jsonl`, request/completion receipts under `artifacts/`. Replay checks card bytes, pinned payload, every document and request identity.
- Safe syntax check: `python -B -m training.dataset_rights_scope --help`.
- Later offline template: `python -B -m training.dataset_rights_scope --documents artifacts/<DOCUMENT_PROOF> --catalog <PINNED_HF_CATALOG> --cards <VERIFIED_CARD_RECEIPTS_DIR> --cache artifacts/<VERIFIED_DATASET_CACHE> --output artifacts/<NEW_RIGHTS_SCOPE> --provenance-assessment`.
- **Gap:** the live tree has no general CLI to fetch/build the required card receipts, nor a generic dataset `CLEAR` → approved production file manifest/plan adapter. Do not substitute metadata `ACCEPTED` or rights `CLEAR` for admission.

## Production preflight, execution and lineage

### 11. Frozen spec/source dry-run — `training/production_spec.py`

- Purpose/class: validate the active sealed registry/spec and show acquisition blockers, cap upper bounds and deficits; `RO` if printed only, `W` if `--output` is supplied. No network, shards or ledger mutation; no prior approval required to inspect. `--receipts` audits checkpoint totals only, **not** payload/shard certification.
- Optional: `--root` (default `.`), `--output` (must not exist), `--receipts`, `--require-ready` (exit 2 if blocked). Inputs: `<root>/training/specifications/{production_corpus_v1,source_registry_v1}.json` and any referenced evidence; output is stdout or a new report JSON. No `--resume`. Missing immutable manifests/evidence are reported/blocked, not invented.
- Safe diagnostic: `python -B -m training.production_spec --root .`.
- Later preflight template: `python -B -m training.production_spec --root <CHECKOUT_WITH_APPROVED_EXTERNAL_EVIDENCE> --output artifacts/<NEW_SPEC_PREFLIGHT_JSON> --require-ready`.

### 12. Production batch coordinator — `training/production_build.py`

- Purpose/class: **authoritative CLI** for approved plan compilation, real per-item acquisition, verification, normalization, screening, quality/language/ownership checks, protected references, global and cross-batch dedup, split, cached tokenization, cumulative accounting, checkpoints, NOTICE and shard export. `--dry-run` is `DRY+W` (creates local runner/SQLite state, zero downloads/tokens); real execution is `W+NET+TA` when approved GitHub payloads are missing, or `W+TA` with verified local `input_path`. Real runs can **mutate the cumulative ledger**. Only immutable per-file `ACCEPT` grants in an approved plan can be scheduled.
- Required for all modes: `--target-tokens` (1..2B); supply `--root`, `--spec`, `--registry`, `--plan`, `--directory`, `--references`, `--tokenizer` explicitly on a clean checkout. Real mode additionally requires external `--approved-plan-sha256`, `--ownership-approval`, `--approved-ownership-approval-sha256`, `--prior-production`, `--corpus-ledger`, `--approved-corpus-head`, plus current governance pins when governance is in force; historical ledger genesis also requires all three approved historical pins. Optional: `--intended-use`, `--decision-receipts` (required for evaluation/commercial-training authorization), `--resume`, `--dry-run`, `--chunk-items`, `--reserve-mib`, `--request-interval`, `--governance-log`, `--approved-governance-sha256`.
- Inputs/outputs: approved registry/spec/plan, protected references, external approval authority and prior-production inventory, frozen tokenizer; writes `runner/plan.jsonl`, inventory/unresolved/progress receipts, build `state.sqlite`, raw/normalized/token caches, screening/quarantine evidence, checkpoints, `exports/<version>/prepared.json`, admission/NOTICE files and token shards. `--resume` requires unchanged externally approved pins and input identities, re-verifies state, and reuses committed cache. Exit 0 means target reached; exit 3 means the approved inventory exhausted below target; exit 2 is a stop/failure. Preparation authorization does **not** authorize training.
- Safe preflight *template* (do not use an unapproved plan): `python -B -m training.production_build --root . --spec <APPROVED_SPEC> --registry <APPROVED_REGISTRY> --plan <APPROVED_PLAN> --references <PROTECTED_REFERENCES> --directory artifacts/<NEW_DIAGNOSTIC_BUILD> --target-tokens 1 --dry-run`.
- **Unexecuted real-production template:** `python -B -m training.production_build --root . --spec <APPROVED_SPEC> --registry <APPROVED_REGISTRY> --plan <APPROVED_PLAN> --references <PROTECTED_REFERENCES> --tokenizer training/resources/phase1/bpe_fitter_optimization_gate_v1/comparison/run-4096-0/tokenizer.json --directory artifacts/<NEW_PRODUCTION_BUILD> --target-tokens <REVIEWED_TARGET> --approved-plan-sha256 <EXTERNAL_PLAN_SHA256> --ownership-approval <EXTERNAL_OWNERSHIP_APPROVAL> --approved-ownership-approval-sha256 <EXTERNAL_APPROVAL_SHA256> --prior-production <COMPLETE_PRIOR_INVENTORY> --corpus-ledger <SHARED_LEDGER_SQLITE> --approved-corpus-head <EXTERNAL_HEAD> --governance-log <EXTERNAL_GOVERNANCE_LOG> --approved-governance-sha256 <EXTERNAL_GOVERNANCE_SHA256> --approved-historical-import-identity <APPROVED_IMPORT_ID> --approved-historical-manifest-identity <APPROVED_MANIFEST_ID> --approved-historical-manifest-sha256 <APPROVED_MANIFEST_FILE_SHA256>`.
- Omit the three historical-import flags only for a ledger **without** historical genesis. `--governance-log` and its digest are a pair when current governance applies. Never fabricate a pin to make the template run.

### 13. One-time historical ledger import — `training/historical_corpus_import.py`

- Purpose/class: reconstruct **the declared retained historical set** from verified accepted-item evidence; `--preview` is `RO`; `--commit` is `W` and **mutates the cumulative ledger once**. No network or new shards. Requires the exact historical manifest; not a general new-source importer. There is no `--resume` flag; commit is once-only/idempotent under its strict identity checks.
- Required: `--root`, `--manifest`, exactly one of `--preview`/`--commit`. Commit additionally requires `--ledger`, independent `--approved-head`, `--approved-import-identity`, `--approved-manifest-identity`, `--approved-manifest-sha256`; optional governance log/hash. Preview prints reconstructed identity and usage; commit writes ledger genesis. Every retained build/item, content hash, split, owner and token count is rechecked. A missing/extra/changed item fails closed.
- Safe syntax check: `python -B -m training.historical_corpus_import --help` (preview requires the separately retained manifest and payloads).
- **Unexecuted authorized-history template:** `python -B -m training.historical_corpus_import --root . --manifest <EXACT_RETAINED_MANIFEST> --preview`; the distinct one-time commit form is `python -B -m training.historical_corpus_import --root . --manifest <EXACT_RETAINED_MANIFEST> --commit --ledger <SHARED_LEDGER_SQLITE> --approved-head <EXTERNAL_GENESIS_HEAD> --approved-import-identity <EXTERNAL_IMPORT_ID> --approved-manifest-identity <EXTERNAL_MANIFEST_ID> --approved-manifest-sha256 <EXTERNAL_MANIFEST_FILE_SHA256>`.

### 14. Cumulative ledger audit/abort — `training/cumulative_accounting.py`

- Purpose/class: `--reconstruct` verifies the externally pinned chain and rebuilds cumulative totals from committed item/build evidence (`RO` in logical effect; SQLite is opened read/write for schema checks). `--abort-build-id` is `W` and **mutates the ledger** by releasing only an active reservation; never a committed build. No network, tokens or shards; no `--resume` flag.
- Required: `--ledger`, `--root`, independently trusted `--approved-head`, and exactly one of `--reconstruct`/`--abort-build-id`. For a ledger with historical genesis, also supply all `--approved-historical-import-identity`, `--approved-historical-manifest-identity`, `--approved-historical-manifest-sha256`. Inputs: ledger plus retained build DBs/payloads and external pins; output: JSON stdout, or changed ledger only for abort. Missing/corrupt/stale chain/payload fails closed. An approved ledger head is **not** to be copied from untrusted local state.
- Safe syntax check: `python -B -m training.cumulative_accounting --help`.
- Later read-only verification template: `python -B -m training.cumulative_accounting --root . --ledger <SHARED_LEDGER_SQLITE> --approved-head <EXTERNAL_HEAD> --approved-historical-import-identity <APPROVED_IMPORT_ID> --approved-historical-manifest-identity <APPROVED_MANIFEST_ID> --approved-historical-manifest-sha256 <APPROVED_MANIFEST_FILE_SHA256> --reconstruct`.
- **Unexecuted recovery template:** `python -B -m training.cumulative_accounting --root . --ledger <SHARED_LEDGER_SQLITE> --approved-head <EXTERNAL_HEAD> --abort-build-id <EXACT_ACTIVE_BUILD_ID>`; use only after explicit recovery review.

## Where the remaining gates actually run

The following are live implementation surfaces, **not additional `python -m` CLIs**. Their checks run inside the approved production coordinator or through a documented Python API. Running a unit module directly will not perform a gate.

| Requested operation | Live enforcement/API | Operator boundary and limitation |
|---|---|---|
| Source identity, license evidence and conditional rights | `training/license_evidence.py` (`resolve_license`, `package_license_matches`); `training/conditional_license.py` (`validate_approval`); `source_discovery`, `source_approval`, `production_acquisition.validate_clearance` | Metadata is not item permission. Conditional licenses require source-specific obligation/approval evidence. No standalone license-verification CLI. |
| File/document clearance | `clearance_evidence`, `source_approval`, `source_admission`, `dataset_clearance`, `dataset_rights_scope`; `production_acquisition.validate_clearance` | Different statuses have different meanings. Only validated production per-file `ACCEPT` grants can enter a production plan. No generic dataset-to-production grant CLI. |
| Raw extraction and deterministic normalization | `dataset_transport.payload_rows`; `production_acquisition.ProductionBuild._acquire/_prepare`; `training/corpus_prep.py` and `training/experiments/representative_mini_corpus.py::normalize_structured_text` | Production normalizes **after** exact payload verification; no standalone production normalization CLI. Historical experiments are not a substitute. |
| Intended-use corpus authorization | `training/corpus_gate.py` (`load_receipts`, `verify_receipt`); `ProductionBuild.authorize_use/export_shards/replay_for_use` | Preparation permission is not evaluation or commercial-training permission. **Genuine Phase 3 operator gaps.** The live system has no CLI to (1) transform a supplied broad review intake into verified pinned discovery seeds/metadata and a controlled registry/approval proposal in bounded batches (the current clearance-evidence CLI also fixes its base registry/approved inputs), (2) build/verify exact-revision HF card receipts consumed by `dataset_rights_scope`, (3) establish the independent source-specific and per-file rights evidence needed to use the first-time repository materializer, or materialize general dataset `CLEAR` evidence into externally approved production grants/plans, (4) assemble the complete externally controlled protected-reference/prior-production inventories, ownership approval, decision receipts and governance events from reviewed inputs, (5) run a single read-only complete build/export/NOTICE/shard/authorization verifier, or (6) perform the old end-to-end hardware training-readiness rehearsal from a tracked CLI. Items (1), (2), (4), (5), (6) largely wrap/validate existing APIs and authority inputs; item (3) still requires source-specific human review and dataset adapters before many Phase 3 candidates can enter production. Do not fill these gaps by bypassing current gates or by treating the review catalog as an approved registry.

## Recommended execution chain

1. Keep the sealed Phase 3 intake as REVIEW. Screen with `source_expansion`; prepare bounded explicit GitHub/HF seed lists for `source_discovery` or `dataset_discovery`. Independent pin/license/category review is required before the next step.
2. For a supported pinned Git repository, use `source_prepare --dry-run`, then the same request for the review cache; use `clearance_evidence`, the narrow `source_approval` if its evidence profile applies, then `source_admission` against the complete approved universe. For a supported pinned HF dataset, use `dataset_transport`, `dataset_clearance`, `dataset_rights_scope`; stop at rights evidence until a reviewed dataset production-grant adapter exists.
3. Supply externally approved plan/ownership/governance pins, complete protected references and prior-production inventory, and the shared ledger/head. Run `production_spec` and a **fresh** `production_build --dry-run`; a dry-run is not an authorization or token yield.
4. Only after separate acquisition approval, run the same `production_build` request without `--dry-run` in a fresh build directory; use `--resume` only for that exact request. It performs acquisition → verified raw bytes → normalization → Phase 2 screening/rights/quality/language/ownership/NOTICE/protected-reference checks → dedup/split → cached tokenizer → accounting/checkpoint → export/shards.
5. Verify the externally pinned cumulative ledger with `cumulative_accounting --reconstruct`, plus the retained build/export/shard and current-governance checks. Preserve new head and approvals outside mutable build state. This still does **not** authorize YUG-100M training.
